# ODIN1 Lite SLAM 点云 Web 预览专项测试（2026-07-31）

> 文档性质：历史设计或历史测试记录。当前运行版网页预览已经改为补偿后的
> `/capture/lidar/points_compensated_enu` 局部东北天点云，并只保留三维视图。
> 本文中的 SLAM 输入、RGB 裁减、世界坐标和俯视图结论不作为当前版本验收依据。


文档状态：静止场景短时实测

本记录用于确定浏览器实时点云预览的输入契约和首版参数。它不证明动态车辆、
隧道场景、长时间稳定性或最终 RK3588 满负载性能。

方案决策更新：测试时评估过里程计配对、车辆局部转换、过滤和体素降采样，但
当前首版已经确定不采用这些处理。首版保持SLAM `odom` 世界坐标，只做5 Hz
限频、RGB字段裁减和最多10,000点限制。以下配对和体素数据作为历史实测依据
保留，不表示首版实现范围。

## 1. 测试目的

本次测试回答以下问题：

1. `/capture/lidar/points_slam` 的实际字段、坐标系、点数、频率和带宽；
2. SLAM 点云与 `/capture/odometry/slam` 是否可以按时间戳配对；
3. 不同体素尺寸对当前实测点云的保留率；
4. Web 预览协议和默认参数应采用什么上限。

## 4. 时间戳与坐标语义

SLAM 点云时间戳测试区间为设备启动后的约179.765–189.443秒，同时系统 Unix
时间约为1,785,464,987秒。两者没有共同时间原点。

因此：

- 不得使用 ROS 节点当前时间减去 `header.stamp` 判断点云是否过期；
- 输入新鲜度必须使用收到消息时记录的单调时钟；
- 浏览器不得直接用传感器时间戳计算端到端延迟；
- `header.stamp` 继续原样保留，用于同一设备时间域内的消息配对。

30帧点云和29帧标准里程计的短时配对结果：

| 指标 | 结果 |
| --- | --- |
| 时间戳完全相同 | 28/30帧 |
| 完整采样窗口内P50/P95差值 | 0 ms / 0 ms |
| 窗口边界最大差值 | 195.528 ms |

最大差值出现在订阅启动和结束边界，是采样窗口没有包含对应里程计消息造成的。
这组结果保留给未来车辆局部视图设计使用。当前首版不订阅里程计，不使用这些
数据做时间戳配对。

消息和驱动接口共同表明SLAM点位于 `device0/odom`。当前RViz的Fixed Frame也是
`device0/odom`，因此首版保持输入坐标和 `frame_id`，不转换到 `base_link`。

| ---: | ---: | ---: | ---: |
| 0.05 m | 1,936–1,962 | 1,950.8 | 19.3% |

原设计建议的0.15 m在当前场景只剩约450点，可能导致画面过于稀疏。当前首版
决定不做体素降采样，本节数据只为未来性能优化保留。

## 6. 对首版 Web 预览的直接结论

建议首版采用以下输入和输出约束：

| 参数 | 建议初值 | 理由 |
| --- | ---: | --- |
| 输入 | `/capture/lidar/points_slam` | 实测稳定约10.27 Hz |
| 输出频率 | 5 Hz | 跳过中间帧，不积累延迟 |
| 最大输出点数 | 10,000 | 接近实测输入上界，最坏xyz负载120 kB/帧 |
| 点数限制 | 确定性等间隔选点 | 只在输入超过10,000点时启用 |
| 输出字段 | xyz FLOAT32 | 裁减RGB后为12字节/点 |
| 坐标系 | 保持输入 `device0/odom` | 与当前RViz Fixed Frame语义一致 |
| 点颜色 | 前端单色 | 首版不传RGB，不做高度着色 |
| 单帧发送上限 | 128 KiB | 覆盖10,000点和24字节协议头 |
| 每客户端队列 | 1帧 | 新帧覆盖旧帧 |
| 最大客户端数 | 4 | 限制网络和复制开销 |

在最坏10,000点、5 Hz时，单客户端点数据约0.6 MB/s，四个客户端约2.4 MB/s。
以上均不含少量WebSocket/TCP帧开销。首版不做体素降采样，应按接近该上限进行
网络和资源测试。

原SLAM消息包含有效RGB。当前首版裁减RGB并使用前端单色，是范围决策，不能
误认为源点云没有颜色。

# RK3588 双网口环境与网络部署

核对日期：2026-08-10

## 1. 适用条件

本项目当前部署脚本只支持双物理以太网口的 RK3588。新机应预先完成：

```text
Ubuntu 22.04
ROS 2 Humble
CPU 架构 aarch64
至少两个物理以太网接口
```

`install.sh` 不安装 Ubuntu，也不安装 ROS 2 本体。缺少 `/opt/ros/humble/setup.bash` 时脚本直接退出。

## 2. 双网口固定分工

默认网络参数如下：

| 对象 | 默认地址 | NetworkManager profile | IPv4 模式 |
| --- | --- | --- | --- |
| RK3588 雷达口 | `192.168.1.200/24` | `capture-lidar` | `manual` |
| ODIN 雷达 | `192.168.1.251` | 无 | 设备固定地址 |
| RK3588 维护口 | `192.168.100.1/24` | `capture-direct` | `shared` |
| 浏览器固定入口 | `http://capture-system.local:8000/` | Avahi/mDNS | 无 |

雷达口和维护口必须绑定两个不同的物理接口。维护口由 NetworkManager `shared` 提供 DHCP，电脑直连时不需要手工设置静态 IPv4。

未指定接口时，脚本优先选择：

```text
雷达口   eth0
维护口   eth1
```

如果设备使用其他接口名，脚本会从 sysfs 识别的物理以太网接口中选择，也可以通过参数明确指定。NetworkManager 启动后，两个目标接口还必须处于受管理状态；如果 netplan renderer 或 NetworkManager 配置把接口标记为 unmanaged，脚本会报错并触发回滚。

## 3. install.sh 的职责

执行：

```bash
sudo bash scripts/deploy/install.sh --variant customer
```

开发环境可使用：

```bash
sudo bash scripts/deploy/install.sh --variant development
```

脚本执行以下操作：

1. 检查 Ubuntu 22.04、aarch64 和 ROS 2 Humble。
2. 保存本次修改前的 hostname、项目环境配置、NetworkManager profile 和相关服务状态。
3. 安装后续编译、运行和网络管理所需的 apt 依赖。
4. 安装或升级到 Node.js 22.13.0 以上。
5. 使用同一个普通用户 ROS Home 执行 `rosdep update`，再由 root 读取同一缓存执行 `rosdep install`，避免 `/home/<user>/.ros` 与 `/root/.ros` 不一致。
6. 检查 Firefly Qt5 的 GLX 插件元数据是否引用缺失文件；只有检测到已实测的精确包不一致时，保守重装 `libqt5gui5`、`qtbase5-dev`、`libqt5opengl5` 和 `libqt5opengl5-dev`。
7. development 变体额外安装 `ros-humble-rosbag2-storage-mcap`。
8. 安装雷达 UDP sysctl 配置。
9. 根据当前 polkit authority 安装 Web 运行用户所需的 NetworkManager 最小权限，并验证实际授权结果。
10. 配置 hostname、Avahi/mDNS、`capture-lidar` 和 `capture-direct`。
11. 使用 `verify_deployment.sh --configured-only` 检查写入结果。
12. 确保运行用户属于 `dialout` 组，用于访问 RTK USB 串口；首次加入后需要注销并重新登录。

脚本明确不执行：

```text
scripts/build/build.sh
scripts/deploy/install_systemd.sh
scripts/operation/run_lan_preview.sh
任何 ROS 2 节点启动
```

因此环境部署、项目编译和节点启动是三个独立步骤。

## 4. 安装前网络要求

apt、NodeSource 和 rosdep 需要互联网连接。建议新机在执行 `install.sh` 前通过 Wi-Fi 或其他不会被本次双网口重配影响的接口联网。

脚本先完成依赖下载，再修改两个有线接口。这样可以避免雷达口和维护口切换为固定用途后失去互联网导致依赖安装中断。物理网口识别直接读取 sysfs，不要求 NetworkManager 在脚本开始时已经运行。启动 NetworkManager 前会先执行 SSH 接口保护；服务启动后再确认雷达口和维护口均由 NetworkManager 管理。

如果当前 SSH 会话使用即将重配的雷达口或维护口，脚本默认拒绝继续。若 NetworkManager 在执行前尚未运行，脚本在启动它之前会把全部物理有线接口视为潜在受影响接口，因此任何有线 SSH 都会被拒绝。推荐使用：

```text
本地显示器和键盘
或
Wi-Fi SSH
```

只有明确接受 SSH 中断风险时才使用：

```bash
--allow-ssh-network-reconfigure
```

## 5. 接口明确指定

例如设备接口为 `eth0` 和 `eth1`：

```bash
sudo bash scripts/deploy/install.sh \
  --variant customer \
  --lidar-interface eth0 \
  --direct-interface eth1
```

需要修改维护网段时：

```bash
sudo bash scripts/deploy/install.sh \
  --variant customer \
  --lidar-interface eth0 \
  --direct-interface eth1 \
  --direct-cidr 192.168.101.1/24
```

雷达网段有变化时必须同时显式修改雷达参数，不应直接沿用默认值：

```bash
--lidar-host-cidr <板端CIDR>
--lidar-device-ip <雷达IPv4>
```

## 6. 配置检查与真实网络验收

环境和网络写入完成后可以随时执行：

```bash
sudo bash scripts/deploy/verify_deployment.sh --configured-only
```

该模式检查：

```text
hostname
Avahi 服务和项目服务文件
NetworkManager
/etc/capture-system/device.env
capture-lidar 的接口、manual、地址和 never-default
capture-direct 的接口、shared、地址和 never-default
polkit `.rules`/`.pkla` 配置及运行用户三个必需 NetworkManager action 的实际 `yes` 状态
sysctl 配置
两个 profile 是否绑定不同物理接口
```

该模式不要求网线当前有链路，适合新机刚完成环境准备时使用。

AIO-3588JQ 的 Firefly Ubuntu 22.04 实机已经确认 polkit 0.105 使用 Local Authority。该环境最终配置文件为：

```text
/etc/polkit-1/localauthority/50-local.d/50-capture-networkmanager.pkla
```

项目要求实际运行用户以下权限全部为 `yes`：

```text
org.freedesktop.NetworkManager.wifi.scan
org.freedesktop.NetworkManager.settings.modify.system
org.freedesktop.NetworkManager.network-control
```

其中 `settings.modify.own` 不属于当前默认授权集合。部署脚本不依据单一版本号假定后端，而是先检测 authority，再以实际权限结果验证；首选格式不生效时才尝试兼容格式。

接好 ODIN 雷达和维护网线后执行：

```bash
sudo bash scripts/deploy/verify_deployment.sh --network-only
```

该模式额外要求：

```text
capture-system.local 能在本机解析
雷达口实际具有 192.168.1.200
到 192.168.1.251 的路由使用雷达接口
该路由源地址为 192.168.1.200
维护口实际具有 192.168.100.1
```

没有实际链路或地址时不会返回 PASS。

## 7. 编译与启动

环境和网络部署完成后，编译继续使用项目现有入口：

```bash
bash scripts/build/build.sh all --release --variant customer
```

开发构建：

```bash
bash scripts/build/build.sh all --release --variant development
```

前台启动完整采集链继续使用：

```bash
bash scripts/operation/run_lan_preview.sh
```

`install.sh` 不替代以上两个入口。

如果以后只需要让 Web 服务开机启动，可以单独执行：

```bash
sudo bash scripts/deploy/install_systemd.sh
```

当前最新项目的 `install_systemd.sh` 只安装 `capture-web.service`，不负责启动完整 ROS 2 采集链。该步骤不属于新机环境与网络部署默认流程。

## 8. 失败回滚

每次 `install.sh` 修改系统前保存：

```text
/etc/capture-system/install_state.json
/etc/capture-system/backups/
```

安装过程发生错误时会自动调用：

```bash
sudo bash scripts/deploy/rollback.sh
```

回滚范围只对应新的 `install.sh` 职责，包括：

```text
hostname
capture-lidar
capture-direct
NetworkManager 和 Avahi 原服务状态
本项目 Avahi 配置
本项目 polkit `.rules` 与 Local Authority `.pkla` 配置的安装前状态
雷达 sysctl 配置
/etc/capture-system/device.env
NodeSource 源和 key 的原状态
```

自动回滚不会卸载已经由 apt、NodeSource 或 rosdep 安装的软件包，也不会修改项目构建产物、Capture System systemd 单元或 `runtime/` 数据。

## 9. 人工清除配置

需要把新机恢复到首次 `install.sh` 前的项目环境和网络状态时执行：

```bash
sudo bash scripts/deploy/clear_config.sh
```

该脚本优先使用首次安装前快照恢复配置。它不会执行以下操作：

```text
卸载 apt 软件包
删除 Node.js
删除 rosdep 已安装依赖
删除 .venv
删除 frontend/node_modules
删除 ros2_ws/build、install、log
停止或删除可选的 `capture-web.service`
删除 runtime
删除 capture.db、tasks、measurements.db、reports
```

如果 `/etc/capture-system/install_state.json` 已丢失，脚本默认拒绝推测原系统状态。确认当前项目网络配置均可删除后，才可显式执行：

```bash
sudo bash scripts/deploy/clear_config.sh --force-without-state
```

该模式无法知道部署前 hostname，因此不会修改 hostname。

## 10. 状态检查

```bash
sudo bash scripts/deploy/status.sh
```

输出来自真实设备，包括 hostname、mDNS、Avahi、NetworkManager、两个有线接口地址、可选 `capture-web.service` 状态、HTTP health、雷达路由、`runtime` 和磁盘剩余空间。Web 服务尚未启动时 systemd 和 HTTP 项显示 inactive 或 unavailable 属于正常现象，不能据此判定环境和网络部署失败。

## 11. 数据边界

部署和恢复脚本不得把现场数据作为系统配置处理。以下内容始终与环境清理分离：

```text
runtime/
runtime/capture.db
runtime/tasks/
每任务 measurements.db
runtime/reports/
runtime/dev-tests/
runtime/settings/
```

需要清理业务数据时必须使用独立、明确的数据维护流程，不应通过部署脚本实现。
